STONEGROVE 0.3.63.34 - Reproducible 30-player server test

From the extracted developer folder:
  python Server/load_test_30.py --seconds 90 --output load30-results-new

Use a new output directory. The tool creates its own SQLite database and saves; it does not attach to the production service or use production accounts. It starts a separate real server process, authenticates 30 accounts through HTTP, then measures 90 seconds of updates and 180 seconds of synthetic movement/combat. Each client sends the same personal-field whitelist as the game client, with one request in flight and up to five polls per second. Gzip is negotiated and transferred payload bytes are measured before decompression. Separate loopback addresses allow account setup without disabling login throttling. Local test traffic bypasses proxy discovery; real clients use native Windows HTTP.

Outputs include result.json, requests.json, metrics.json, server.log and the isolated test saves. CPU is percent of one logical core: 200% means two cores. Windows reports current RSS/private process memory; Linux uses /proc RSS and anonymous RSS for the private-memory approximation. Run this on the intended cloud hardware for hosting decisions. Server and synthetic clients share the machine, although server CPU/memory are measured separately.

This is a capacity sample, not a multi-hour soak. It excludes rendering, WAN/TLS latency and mixed cave/camp/crafting/spell workloads. The default world selects combat targets for all clients. Functional gameplay checks exercise those other systems separately. Never treat successful connections alone as proof of adequate response latency. Production SQLite durability settings and existing save/network packing remain unchanged.

Client gzip integration follows Microsoft's WinHTTP decompression option documentation:
https://learn.microsoft.com/en-us/windows/win32/winhttp/option-flags#winhttp_option_decompression
